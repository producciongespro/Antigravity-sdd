📖 1. ¿Qué es Spec-Driven Development (SDD)?

El Desarrollo Guiado por Especificaciones (SDD) es una metodología de ingeniería de software en la cual una especificación viva, formal y versionada actúa como la Única Fuente de Verdad (Single Source of Truth - SSOT) antes de escribir o modificar una sola línea de código de producción.

💡 La Regla de Oro del SDD
"Si no está en la Especificación (docs/SPEC.md), no existe. Si está en la Especificación, el software está obligado a cumplirlo matemática y sensorialmente."

La Metáfora de la Construcción Civil

❌ Desarrollo Tradicional / Caótico con IA

Pedirle a un albañil que levante paredes en un terreno vacío diciéndole: "Hazme una sala bonita y luego vemos dónde va el baño". El resultado inevitable son demoliciones continuas, vigas mal calculadas y colapso estructural.

✅ Spec-Driven Development (SDD)

El arquitecto diseña el plano formal (SPEC.md), calcula cargas de ingeniería (ARCHITECTURE.md) y define tolerancias de materiales (RULES.md). Ningún operario pega un solo bloque sin verificar el plano.

🔬 2. El Arnés de Pruebas (The Test Harness) - El Órgano Sensorial

Un Modelo de Lenguaje (LLM) es un procesador de texto probabilístico: no tiene ojos, manos ni navegador para comprobar físicamente si un botón hace clic o si una tabla se actualizó. El Arnés de Pruebas (Test Harness) es el andamiaje instrumental que le otorga percepción sensorial y retroalimentación empírica en tiempo real.

🔄 3. El Ciclo de Vida: Rojo $ ightarrow$ Verde $ ightarrow$ Refactor

Fase Color Acción en el Laboratorio Propósito / Objetivo
1. Fase Roja 🔴 FAIL Diseñar la prueba antes de programar y verla fallar con un error explícito. Demostrar que la prueba es real y detecta la ausencia de la función.
2. Fase Verde 🟢 PASS Escribir el código mínimo necesario para que la prueba pase a verde. Alcanzar el cumplimiento estricto del contrato sin sobre-ingeniería.
3. Refactorización 🔵 CLEAN Reorganizar taxonomía, limpiar deuda técnica, optimizar código. Mejorar la calidad sin miedo: el arnés garantiza que nada se rompió.
⚠️ La Trampa de las Pruebas Falsas Positivas
Si creas una prueba y pasa en verde de inmediato sin que hayas programado nada, la prueba no sirve. La Fase Roja es la garantía científica de que la prueba realmente detecta la falta de la función.

🚧 4. Guardrails: Las Barandillas de Seguridad (Explicado para Todos)

La palabra Guardrail significa literalmente la barandilla de contención metálica que ves al borde de una carretera en la montaña. Tú sabes manejar, pero si hay hielo, la barandilla físicamente te impide caer al abismo.

4 Ejemplos Visuales de la Vida Real:

1. La puerta del microondas

Si abres la puerta mientras calienta, el microondas se apaga en el acto. Es un guardrail físico: no confía en que recuerdes apagarlo; bloquea el peligro por diseño.

2. Las rueditas de la bicicleta infantil

No pedalean por el niño, pero si la bicicleta se inclina peligrosamente hacia un costado, tocan el suelo e impiden una caída grave.

3. El enchufe de 3 clavijas (con polo a tierra)

Tiene una clavija redonda más larga. Es geométricamente imposible enchufarlo al revés; su propia forma actúa como guardrail.

4. El script automatizado (check:guardrails)

Escanea 47 verificaciones en 5 fases en ~50ms e impide que se suba código que viole el idioma español, toque storage directo o rompa aserciones.

Los 4 Niveles de Guardrails en Desarrollo con IA:

  • 1. Guardrails de Instrucción (app/AGENTS.md, docs/RULES.md): Reglas escritas que prohíben alucinar o inventar APIs.
  • 2. Guardrails Estructurales (Scripts y CI/CD - scripts/guardrails.js): 47 verificaciones automáticas por terminal antes de compilar o hacer commit.
  • 3. Guardrails de Acero (Git Pre-commit Hook): Bloqueo físico en el sistema de control de versiones: si un solo guardrail falla, el commit es abortado de raíz.
  • 4. Guardrails de UX (ConfirmModal): Modales táctiles flotantes que impiden desmarcar compras por error al caminar ("anti-dedazos").

🧰 5. Skills (Habilidades): La Carpeta de Especialidad de la IA

Un Skill es un paquete modular de instrucciones avanzadas, scripts auxiliares y plantillas que enseñan a la IA a realizar una tarea especializada sin necesidad de reentrenar el modelo base.

Carpeta de Recetas del Chef
El modelo base sabe cocinar en general; al activar el skill generative_ui o automation, abre el manual técnico del chef pastelero y opera con precisión de especialista.

🔌 6. MCP (Model Context Protocol): El USB-C Universal de la IA

El Model Context Protocol (MCP) es un estándar abierto desarrollado por Anthropic para permitir que los asistentes de IA se conecten de forma segura a fuentes de datos locales, servidores, repositorios GitHub, bases de datos SQL y herramientas empresariales mediante un protocolo cliente-servidor estandarizado.

👥 7. Arquitectura de Agentes, Subagentes y Slash Commands

  • Humano (Christian Vargas A.): Conduce el proyecto, define requerimientos de negocio y aprueba las especificaciones.
  • Agente Orquestador (Antigravity): Mantiene la visión general, conversa con el humano, actualiza MEMORY.md y supervisa el cumplimiento del contrato.
  • Subagentes Especializados: Asistentes efímeros que el orquestador despierta para tareas aisladas (Investigador para leer documentación sin saturar la conversación, Tester para certificar calidad).
  • Slash Commands (/): Atajos rápidos en la caja de texto (como /plan, /goal, /boost) para activar flujos de trabajo de un solo toque.

📋 10. Checklist Profesional y Protocolo de Trabajo Definitivo

  1. Definir y Acordar: Entender el problema de negocio con el usuario y sponsor.
  2. Documentar en la Spec: Redactar la regla en docs/SPEC.md (subir versión SemVer).
  3. Diseñar el Caso de Prueba: Agregar la aserción en tests/harness.html o tests/e2e.test.jsx con código RF-*.
  4. Comprobar el Fallo Rojo: Re-ejecutar el arnés y certificar el fallo científico (Fase Roja).
  5. Escribir el Código Mínimo: Modificar los componentes y servicios en src/ hasta lograr Verde.
  6. Ejecutar Guardrails: Correr npm run check:guardrails en terminal (47/47 en verde) y suite sensorial E2E (9/9 flujos).
  7. Registrar en Memoria: Guardar el ADR y lecciones aprendidas en docs/MEMORY.md.
  8. Commit Semántico en Git: El Pre-commit Hook valida los 47 guardrails y autoriza el commit atómico.

💡 12. Preguntas y Respuestas Frecuentes (Banco Extendido de Repaso - 21 Consultas Clave)

Compilación exhaustiva de las consultas reales planteadas por Chris durante nuestras sesiones de laboratorio, con las explicaciones conceptuales y prácticas que sustentan la arquitectura.

P1 ¿Por qué no programamos directamente la interfaz o la base de datos en vez de escribir primero la especificación?

Porque sin especificación previa, la IA programa por adivinanza estadística (alucinación funcional). Cuando programas primero la UI, descubres a mitad de camino que faltan campos relacionales o que el borrado en cascada rompe la vista. En SDD, la especificación en docs/SPEC.md es el plano formal aprobado: programar se convierte en rellenar contratos exactos, reduciendo retrabajos a cero.

P2 ¿Qué diferencia hay entre una prueba unitaria común y un "Arnés de Pruebas"?

Una prueba unitaria típica verifica una función aislada fuera de contexto. El Arnés de Pruebas (Harness) es un órgano sensorial completo: levanta la aplicación, simula el entorno físico de ejecución, inyecta estímulos secuenciales de usuario (flujos de interacción) y ofrece un tablero visual con telemetría en tiempo real accesible tanto para el copiloto de IA como para el auditor humano.

P3 ¿Por qué es tan peligroso saltarse la "Fase Roja" en el ciclo de pruebas?

Saltarse la fase roja es como instalar una alarma contra incendios y nunca probar si suena cuando hay humo. Si la prueba pasa en verde sin haber programado la función, estás ante un falso positivo: una prueba mal escrita que siempre aprueba, dando una falsa sensación de seguridad que oculta bugs críticos en producción.

P4 ¿Qué sucede si la IA inventa una función o atributo que no estaba en SPEC.md?

Ocurre una violación de contrato. Los Guardrails automáticos (Fase 4: Linter de Dominio) y el arnés detectan la discrepancia y el sistema falla. En SDD, cualquier adición técnica debe nacer como una propuesta en docs/SPEC.md, aprobada por el sponsor e incrementando la versión SemVer formal.

P5 ¿Por qué los Guardrails son más rápidos que las pruebas tradicionales en navegador?

Porque los 47 Guardrails Maestros se ejecutan puramente en Node.js analizando el árbol sintáctico (AST) de los archivos, expresiones regulares de texto y pruebas en memoria (sandbox MockStorage), tardando menos de 50 milisegundos, sin la sobrecarga de levantar ventanas gráficas de navegador.

P6 ¿Qué es un Skill en Antigravity y cuándo conviene activarlo?

Un Skill es una carpeta modular de instrucciones y utilidades que capacita a la IA en una especialidad concreta (por ejemplo, generative_ui para crear widgets visuales o automation para tareas programadas). Conviene activarlo cuando la tarea requiere conocimiento experto que excede el modelo base.

P7 ¿En qué se diferencia MCP (Model Context Protocol) de una API tradicional?

Una API REST o GraphQL tradicional requiere código cliente personalizado para cada endpoint y proveedor. MCP es un conector estándar universal (como el USB-C): un solo protocolo mediante el cual la IA descubre herramientas, recursos y esquemas de datos expuestos por cualquier servidor compatible sin adaptadores ad-hoc.

P8 ¿Por qué utilizamos subagentes en lugar de hacer todo con el agente principal?

Para evitar la saturación de la ventana de contexto. Cuando un subagente investiga código o lee logs masivos, lo hace en un hilo aislado; solo devuelve el resumen sintetizado al agente orquestador, manteniendo la conversación principal limpia, rápida y enfocada.

P9 ¿Qué rol cumplen los Slash Commands en el flujo diario de trabajo?

Son aceleradores cognitivos: comandos como /plan, /goal o /boost activan directamente flujos de trabajo multi-paso prediseñados, evitando redactar instrucciones repetitivas en cada solicitud.

P10 ¿Por qué prohibimos a los componentes de React llamar directamente a localStorage?

Por el principio de Aislamiento de Capas (Regla innegociable verificada por la Fase 4 de Guardrails). Si la UI llama directo a localStorage, se vuelve imposible migrar de motor, agregar validaciones o probar en memoria. Al pasar por SupermarketStorage, centralizamos integridad referencial, sanitización y tolerancia a fallos.

P11 ¿Qué es un ADR (Architectural Decision Record) y por qué los registramos en MEMORY.md?

Un ADR es un registro formal que documenta el contexto, la decisión técnica tomada y sus consecuencias. En nuestro laboratorio contamos con 22 ADRs formales (ADR-01 a ADR-22) que aseguran que el razonamiento detrás de decisiones críticas (como adoptar Tailwind v4, modal anti-dedazos o tokens WCAG AAA) no se olvide entre sesiones.

P12 ¿Cómo garantiza el sistema que ninguna tarea se dé por terminada antes de tiempo?

A través de la Definición de Terminado (DoD) en docs/RULES.md. Una tarea solo está lista si tiene: 1. Especificación formal, 2. Caso en arnés, 3. Fase roja certificada, 4. Fase verde alcanzada, 5. Los 47 guardrails aprobados, 6. 9 flujos E2E aprobados, 7. ADR asentado en docs/MEMORY.md y 8. Commit validado por el Pre-commit Hook.

P13 ¿Por qué eliminamos window.confirm en el modo de compra táctil en tienda?

Porque el cuadro de diálogo nativo del navegador (window.confirm) bloquea el hilo de ejecución, es inaccesible visualmente y tiene botones pequeños propensos a pulsaciones accidentales con una sola mano. Fue reemplazado por ConfirmModal.jsx (RF-4.6), un modal flotante con botones táctiles gigantes optimizados para el pulgar.

P14 ¿Cómo opera la auto-recuperación ante datos corruptos en el almacenamiento (RNF-02)?

El servicio SupermarketStorage envuelve todas las lecturas en bloques try/catch con validación de esquemas. Si un usuario o script introduce JSON malformado, el servicio detecta la anomalía, restaura silenciosamente las tablas base vacías e impide que la aplicación caiga en pantalla blanca.

P15 ¿Cómo funciona la migración transparente de esquemas al vuelo (RNF-03)?

Al arrancar la aplicación, el servicio detecta si existen tablas en inglés de la v2.0 (products, lists, list_items). Si las encuentra, ejecuta un mapper en memoria que traduce claves y estados al español canónico (productos, listas, enCarrito), persistiendo el nuevo formato sin pérdida de datos para el usuario.

P16 ¿Por qué adoptamos la navegación lateral estilo AdminLTE en el módulo de gestión (RF-5.5)?

Para separar limpiamente las responsabilidades visuales. El Catálogo de Despensa y las Listas de Compras tienen naturalezas distintas: la barra lateral permite saltar entre ambas con contadores numéricos en vivo sin recargar la página ni saturar la pantalla con formularios apilados.

P17 ¿Qué ventaja tiene contar con un panel de Guardrails dentro de la propia interfaz web (RF-5.3)?

Democratiza la auditoría técnica. Cualquier usuario, evaluador o sponsor puede verificar visualmente la salud del sistema (los 47 puntos en verde) con un solo clic en la aplicación web, sin necesidad de abrir una terminal o instalar Node.js.

P18 ¿Cómo se configuran los ganchos de Git mediante .githooks y core.hooksPath para trabajar en equipo?

La carpeta .git/hooks/ no se versiona en Git. Al crear la carpeta versionada .githooks/ con el script ejecutable pre-commit y ejecutar git config core.hooksPath .githooks (automatizado con npm run setup:hooks), el "Guardrail de Acero" se comparte con todo el equipo, forzando la evaluación de los 47 guardrails en cualquier máquina que clone el proyecto.

P19 ¿Cómo logra Vitest + JSDOM ejecutar las pruebas E2E en ~2 segundos sin navegadores pesados?

En lugar de levantar navegadores Chromium reales (como Cypress o Selenium) que tardan decenas de segundos, JSDOM emula toda la API del DOM puramente en memoria dentro de Node.js. Al combinarse con React Testing Library, simula eventos táctiles, clics y cambios de vista con fidelidad absoluta a la velocidad de la CPU en milisegundos (9 flujos completos en ~2.5s).

P20 ¿Por qué organizamos la aplicación en un flujo cronológico de 3 momentos (En casa, En tienda, Laboratorio)?

Porque el software debe alinearse con la psicología humana y no con la estructura de sus tablas relacionales. El usuario vive 3 momentos claros: 1. Planificar la compra en casa (Paso 1: Gestión), 2. Hacer las compras caminando en tienda (Paso 2: Modo Súper Táctil) y 3. Auditar la calidad del sistema (Paso 3: Laboratorio SDD). Esta arquitectura mental elimina fricción y maximiza la usabilidad.

P21 ¿Cuándo usar una Especificación Centralizada (docs/SPEC.md) versus Specs Locales por Componente, y quién las redacta?

2. ¿Centralizado o Local?: Para el 90% de las aplicaciones completas (como SuperCarrito), el patrón centralizado en docs/SPEC.md es el estándar óptimo: evita la fragmentación de contexto del LLM y ofrece una visión integral del modelo relacional. Los specs locales co-localizados se reservan para design systems aislados o monorrepos masivos.
